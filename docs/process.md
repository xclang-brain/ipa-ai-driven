# 開発の進め方

このリポジトリの開発は、IPA「[AI時代の要求管理ハンドブック](https://www.ipa.go.jp/digital/kaihatsu/rqr7mi000000f5up-att/req-mgmt-hb.pdf)」Version 1.0.0 に沿って進める。この文書は、そのための決まりと手順を定める。作業する人と AI は、作業の前にこの文書を読む。

ハンドブックの要点は [handbook-summary.md](handbook-summary.md) にまとめてある。判断に迷ったときは、ハンドブックの該当する章を読む。

## 1. 守る決まり

| 番号 | 決まり | ハンドブックの根拠 |
|---|---|---|
| P-1 | 要望をそのまま実装しない。要望、要求、要件の順に整理し、目的を確かめてから作るものを決める | 1.2節、1.3節 |
| P-2 | 既存のやり方や道具を前提にしない。実現手段は、AI を使わない方法も含めて比べてから選ぶ | 1.4節、2.3節、8.5節 |
| P-3 | 台帳を先に更新し、実装はそのあとに行う。台帳にない要件は実装しない | 2.6節、7.2.8節 |
| P-4 | 要件には、受入条件と確かめ方を書く。確かめられない要件は書き直す | 2.4節、2.5節 |
| P-5 | 要求、要件、テストの対応を保つ。テストの名前には要件IDを含める | 11章 |
| P-6 | AI の出力は候補として扱う。要求の採用、優先度、ベースライン、変更の承認、移行後の文書の承認は、人が行う | 6.7節、6.8節 |
| P-7 | AI を使う箇所には、AI が迷ったときや読み取れないときの振る舞いを決める。推測で埋めない | 5.3節 |
| P-8 | 変更は記録する。理由を「環境の変化」「学習による変更」「初期の定義の不備」に分ける | 11.5節 |
| P-9 | 依頼者の発言と、作成者が補ったことを区別して記録する。確認を得ていないことは、得ていないと書く | 2.5節、6.7節 |
| P-10 | 確かめていないことを、確かめたように書かない。どの環境で何を確かめたかを書く | 5.6節 |

## 2. 工程と成果物

ハンドブック 7章の12の工程と、このリポジトリの成果物の対応を示す。工程は一方向には進まない。あとの工程で分かったことは、前の工程の成果物に戻って反映する。

| 工程 | 成果物 | 更新するとき |
|---|---|---|
| 1. 目的・ミッションの確認 | [01-purpose.md](01-purpose.md) | 目的、成功の基準、リスクが変わったとき |
| 2. ステークホルダーの特定 | [02-stakeholders.md](02-stakeholders.md) | 関係者が増えた、担当が決まったとき |
| 3. 要求獲得 | `03-hearing-NNN.md`（回ごとに追加） | 依頼者から新しい要望や回答を得たとき |
| 4. 要求分析 | [04-analysis.md](04-analysis.md)、`requirements/requirements.yaml` | 要求を追加・変更するとき。手段を選び直すとき |
| 5. 要求仕様化 | [05-specification.md](05-specification.md)、`requirements/system-requirements.yaml` | 要件や成果物の書式を追加・変更するとき |
| 6. モデリング | [06-model.md](06-model.md) | 流れ、データ、AI の使い方、状態が変わったとき |
| 7. 要求評価・妥当性確認 | [07-evaluation.md](07-evaluation.md) | 試行や依頼者の環境での確認を行ったとき |
| 8. 要求ベースライン化 | 台帳の `version` と各要求の `status` | 依頼者が合意したとき |
| 9. 実現手段への接続 | `src/`、`tests/`、`.github/agents/`、[traceability.md](traceability.md)、[runbook.md](runbook.md) | 実装するとき |
| 10. 運用・監視 | 未作成（5章を参照） | |

`requirements.md`、`system-requirements.md`、`traceability.md` は、`python tools/render_ledger.py` が台帳から出力する。直接は編集しない。

## 3. 作業の種類ごとの手順

### 3.1 新しい要望が出たとき

1. 依頼者の発言を、`03-hearing-NNN.md` に記録する。発言はなるべく元の言葉で書く。
2. 背景の目的を確かめる。目的が分からない場合は、依頼者に聞く。聞くことは、依頼者にしか答えられないことに絞る。
3. 要求候補を `requirements/requirements.yaml` に追加する。状態は `候補` とする。作成者が補った要求は、`source` を `作成者` とする。
4. `04-analysis.md` に、ほかの要求との衝突、実現手段の比較、採用する手段と理由を書く。手段の良し悪しは、実際の文書で試してから判断する。
5. 依頼者に、採用する手段と範囲について合意を求める。合意を得たら、状態を `合意済み` にし、台帳の版を上げる。
6. 3.2 に進む。

### 3.2 要件を追加・変更して実装するとき

1. `requirements/system-requirements.yaml` に、要件、由来（`derived_from`）、受入条件、確かめ方を書く。
2. 書式や検査の決まりが変わる場合は、`05-specification.md` を更新する。流れやデータが変わる場合は、`06-model.md` を更新する。
3. テストを書く。名前は `test_fr011_...` のように、要件IDで始める。
4. 実装する。
5. `pytest` と `python tools/render_ledger.py` を実行する。後者は、自動テストで確かめるはずの要件にテストがない場合に、誤りとして知らせる。
6. ベースラインのあとの変更は、`change-log.md` に1行足す。
7. 要件の `status` を更新する。自動テストで受入条件を確かめたら `検証済み`、依頼者の環境での確認が残っていれば `実装済み` とする。

### 3.3 変更の大きさと、戻る工程

変更の内容によって、戻る工程が変わる（ハンドブック 11.5節）。

| 変更の内容 | 例 | 戻る工程 |
|---|---|---|
| 目的や成功の基準が変わる | 移行の対象を、開発部門の文書から全社の文書に広げる | 工程1。要求を導き直し、新しいベースラインを設定する |
| 要求や業務の流れが変わる | 正本を Markdown に移行する方針をやめる | 工程4 |
| 実現手段や要件が変わる | 図の記法を変える。描画の方法を変える | 工程5 |
| 要求は妥当で、実装が満たしていない | 検査が欠落を見逃す | 戻らない。不具合として直し、再発を防ぐテストを足す |

### 3.4 新しい種類の文書を対象に加えるとき

Word の文書、貼り付け画像、ファームウェアに特有の文書（レジスタマップ、タイミング図など）を加える場合は、3.1 から始める。実際の文書か、同じ特徴を持つ公開の文書で、何が取り出せて何が取り出せないかを先に確かめる。

### 3.5 依頼者の環境で確かめたとき

1. 結果を `07-evaluation.md` に追記する。確かめた環境、日付、結果を書く。
2. うまく動かなかった点は、原因を調べ、3.3 の表で扱いを決める。
3. 該当する要件の `status` を更新する。

## 4. AI に任せる範囲と、人が決めること

| 事柄 | 担い手 |
|---|---|
| 要求候補の整理、矛盾や抜けの指摘、手段の比較の下書き | AI |
| 要求の採用、優先度、範囲、ベースライン | 依頼者 |
| 要件、テスト、実装、文書の作成 | AI。台帳に基づく |
| 文字と表の取り出し、文字の照合 | プログラム |
| 図の書き起こし、書き起こしの確認 | AI（Copilot CLI） |
| 移行後の文書を正本として承認する | 人 |
| リスクを受け入れる判断、設計情報を渡してよい AI の範囲の判断 | 依頼者 |

設計文書を渡してよい AI は、GitHub Copilot に限る（REQ-006）。ほかの AI サービスや外部のサービスに、設計文書の内容を送らない。

## 5. まだ着手していない工程

| 工程 | 着手する時期 | 決めること |
|---|---|---|
| 10. 運用・監視 | 依頼者の実際の文書を移行し始めるとき | 監視する項目（検査の不合格の件数、要確認の印の件数、人が直した件数など）、見直しのきっかけ、責任者 |
| 12. 廃止・移行 | 原本を正本でなくすとき | 原本の保管場所と保管期間、移行済みであることの示し方（REQ-015） |

## 6. 作業を終える前の確認

- [ ] 台帳（要求、要件）が、実装と合っている
- [ ] `pytest` がすべて合格する
- [ ] `python tools/render_ledger.py` が誤りなく終わり、出力をコミットに含めた
- [ ] ベースラインのあとの変更を `change-log.md` に書いた
- [ ] `README.md` の進み具合が、現状と合っている
- [ ] 確かめていないこと、依頼者の確認を得ていないことを、文書に書いた
- [ ] 依頼者への報告で、お願い・判断してほしいことと、作業の記録を分けた
