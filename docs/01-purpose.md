## 1. 背景

- 対象は、組み込み機器のファームウェア開発部門である。
- GitHub Copilot を導入済みで、補助的な利用はできている。AI が自律的に作業を進める使い方（AI 駆動開発）の環境は作れていない。
- 依頼者が挙げた最大の課題は、既存ドキュメントの知識を AI が使えないことである。
  - 既存ドキュメントのほとんどは Word と Excel で作られており、Copilot が内容をうまく理解できない。
  - MarkItDown などの変換ツールを試したが、レイアウトが崩れる。Word 内の図形や Excel 内の画像を抽出できないことも多い。

## 2. 要望と、その背景にある目的

| 区分 | 内容 | 出どころ |
|---|---|---|
| 要望 | 既存の Word / Excel ドキュメントを AI に理解させたい | 依頼者の発言 |
| 背景の目的 | AI が自律的に開発作業を進められる環境を早く作りたい | 依頼者の発言 |

「ドキュメントを変換する」は、目的を達成する手段の一つである。ほかの手段（正本を Markdown に移行する、必要な知識だけを構造化データとして抜き出す、検索の仕組みを通して AI に渡す、など）との比較は、工程4（要求分析）で行う。

## 3. ミッション（暫定）

ファームウェア開発に必要な既存ドキュメントの知識を、AI が正しく参照できる形で提供し、AI に任せられる開発作業の範囲を広げる。

## 4. 価値を受ける人

| 対象 | 得られる価値 |
|---|---|
| ファームウェア開発者 | 仕様の調査や転記の時間が減る。AI に任せられる作業が増える |
| 部門 | AI 駆動開発の環境を整えるまでの期間が短くなる |

## 5. 成功の基準（候補。未合意）

依頼者の発言は「AI が自律的に動く環境を早く作れるようになる」である。このままでは達成を判定できないため、測れる形の候補を挙げる。採否と水準は工程4で決める。

| 番号 | 候補 | 測り方の案 |
|---|---|---|
| S-1 | AI が、提供された知識だけを使って、原本の内容に関する質問に正しく答えられる | 文書ごとに確認用の質問と正解を用意し、正答率を測る |
| S-2 | 図と表の情報が欠落しない | 原本の図・表の数に対し、内容を再現できた数の割合を測る |
| S-3 | 人手による修正の時間が、手作業での書き起こしより短い | 1文書あたりの作業時間を比べる |
| S-4 | AI が、仕様に基づく開発作業を人の介入なしで完了できる範囲が広がる | 対象とする作業を決め、導入の前後で比べる |

## 6. 避けたいリスク（候補。未確認）

依頼者は「今は思い浮かばない」と回答した。以下は作成者が挙げた候補であり、依頼者の確認が必要である。

| 番号 | リスク | 理由 |
|---|---|---|
| K-1 | 変換や抽出の誤り（レジスタアドレス、ビット定義、タイミング値など）に気づかず、AI が誤った実装をする | ファームウェアでは数値1つの誤りが不具合になる。もっともらしい誤りは人も見落としやすい |
| K-2 | 設計情報を、許可されていない外部サービスに送る | 図の読み取りに AI を使う場合、文書の内容を外部に送ることになる |
| K-3 | 原本と変換後の文書の二重管理になり、どちらが正しいか分からなくなる | ハンドブック 14 章は、AI に文書を使わせる条件として正本の明確化を挙げている |
| K-4 | 原本の更新が変換後の文書に反映されず、AI が古い情報を使う | 同上（版と改定履歴の管理） |

## 7. ヒアリング第1回で決まった前提

| 項目 | 内容 |
|---|---|
| 対象の文書 | 仕様書・設計書（Word、Excel）、手順書・規約・議事録。Excel の図形で描かれた UML を含む |
| 正本 | Markdown などに移行し、移行後の文書を正本とする |
| 使える AI | GitHub Copilot のみ |
| AI に任せたい作業 | 仕様に基づく実装・修正、仕様の調査・質問への回答、テストの作成、仕様とコードの整合確認 |

正本を移行すると決まったため、リスク K-3 と K-4 は「移行後に原本をどう扱うか」の問題に変わる。K-1 は、移行時の誤りがそのまま正本の誤りになるため、重要度が上がる。
